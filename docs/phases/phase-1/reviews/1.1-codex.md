1. **P1 — Deadline handling gives the engine and output different access states.** [internal/load/load.go:200](internal/load/load.go:200)  
   `wait` preserves settled pre-deadline states in `acc`, but returns `final` unchanged. `Compute` consumes `final.Access`, while `Result.Inputs` comes from `acc`. If cancellation records an error on a reopened watch—as the comment explicitly anticipates—the engine treats an input as unavailable while the view considers it OK. For example, `process.Kube.Controller` can return `Observed:false`, producing “no controller Deployment” despite a loaded Deployment, with no corresponding incomplete entry. The model and output need one consistent access-state decision.

2. **P2 — The committed module cannot build independently of the workspace bridge.** [go.mod:6](go.mod:6), [.github/workflows/ci.yaml:23](.github/workflows/ci.yaml:23)  
   `go.mod` requires `9f44baa`, which lacks APIs used by this implementation, including `Registry.Process` and `cache.ProxyPodsGVR`. Local verification substitutes `5737a14`; CI also substitutes it through `go.work`. R5/R11 authorize this development bridge, but the plan explicitly requires a kgateway-ui tag at 1.1 close. Publishing the commit alone does not fix standalone consumers or downstream builds through `pkg/cli`; the module pin must change.

3. **P3 — The lifecycle “failure-after-watches-open” case can pass without experiencing the failure.** [internal/app/lifecycle_test.go:45](internal/app/lifecycle_test.go:45)  
   The injected response waits until LIST completion plus 200 ms. Core readiness can complete earlier, allowing `version` to return successfully and cancel that request before the 500 is sent. Rule hits and `WatchesSeen` increment before the hold, so both assertions still pass. The test asserts neither a failed input nor its warning. Consequently, it does not establish cleanup after the advertised failure; the exit-1 cases all fail before watches open. Hold another required input long enough to observe the failure and assert its observable result before checking cleanup.

4. **P3 — The classic watch-denied test rejects behavior the approved design permits.** [internal/load/load_test.go:119](internal/load/load_test.go:119)  
   This assertion requires a non-OK input after an immediate WATCH 403. Design §6.3 explicitly permits LIST synchronization to win that race, yielding correct complete data and success. The test therefore depends on scheduling rather than the stated invariant. It should accept either complete fixture data or a denied result, while rejecting empty/partial successful output. The held-watch harness test verifies fault injection, not that command-level invariant.

5. **P4 — Missing requested GVRs silently bypass readiness validation.** [internal/load/load.go:135](internal/load/load.go:135)  
   A requested GVR absent from `Inputs` is ignored, so `Load` can succeed without establishing that the requested resource was acquired. This becomes relevant when 1.2 resolves user kinds and vendor descriptors against served versions. The ledger already defers it to 1.2.1; that step must either establish and test the resolver guarantee or make the loader reject missing requested inputs.
