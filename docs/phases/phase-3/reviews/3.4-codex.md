I would keep Phase 3.4 open. The in-process GET removes the loopback listener, and the HTTPRoute list now returns control when a context-blind request stalls. Two correctness gaps remain in deadline handling and SPDY error handling.

### P1 · Correctness

1. **A result can win after its deadline.** `FetchGateway` returns the worker result unchanged if it wins the `select`. When the result and `ctx.Done()` are both ready, Go may choose either. A worker that finishes just after cancellation can therefore return a successful `Capture` whose tunnel is already closing, instead of returning `context.DeadlineExceeded` at the package boundary. The HTTPRoute wrapper has the same race. If a successful list wins, `routesLive` can render and exit 0 because its timeout branch requires a non-nil error. [fetch.go:148](/Users/ddoyle/Development/claude/kgwctl-claude-phase3/internal/proxydump/fetch.go:148) · [proxy_routes.go:250](/Users/ddoyle/Development/claude/kgwctl-claude-phase3/internal/app/proxy_routes.go:250) · [proxy_routes.go:292](/Users/ddoyle/Development/claude/kgwctl-claude-phase3/internal/app/proxy_routes.go:292)
2. **A delayed SPDY error can turn a truncated dump into a successful `proxy dump`.** `portStream.Read` returns the data stream’s original EOF if the error stream takes more than one second to finish. For an HTTP 200 whose body is delimited by connection close, EOF ends the body successfully. If the data stream ends after a partial body and the forward error arrives after that grace period, `io.Copy` succeeds and the command exits 0 with the partial bytes. The existing SPDY error test sends the error before closing the data stream and before writing HTTP headers.
